# K 线完整性治理设计文档

**日期：** 2026-04-16

**状态：** 已在对话中确认方案，待进入实施计划阶段

## 一、背景

当前仓库已经具备以下与日线数据相关的能力：

- `src/services/market_data_sync_service.py`：按交易日执行增量同步与历史回填
- `src/services/screening_task_service.py`：筛选主流程中的 ingest 阶段会触发日线同步
- `src/services/factor_service.py`：基于本地 `stock_daily` 推导最新可用交易日与因子快照
- `scripts/fast_backfill.py`、`scripts/data_reset_and_backfill.py`：历史补数与数据重建脚本
- `src/scheduler.py`、`main.py`：已有定时任务能力

现状存在两个已经确认的问题：

1. `stock_daily` 中存在真实缺口，且不是单只股票偶发缺失，而是某些交易日只写入了极少数股票数据。
2. 当前同步链路允许“覆盖率够高就跳过剩余缺口”，导致缺口可以被记录但不被补齐，后续又可能被主流程视作“可继续运行”。

此外，还存在一类长期多源获取失败的股票，例如：

- `000552`
- `300067`
- `301022`
- `603056`

这类股票不能因为反复失败而让任务长期阻塞，但又不能把所有同步失败都简单地视为“天然可跳过”。

因此，本次设计的核心目标是：

- 让非豁免股票的 K 线数据保持完整
- 让临时失败不阻塞主流程，但必须进入补偿闭环
- 让长期确实无数据的股票通过受控豁免机制排除在完整率分母之外

## 二、目标

本次设计要建立一套“同步 + 审计 + 补偿 + 豁免”的完整闭环，使系统能够：

- 在每个交易日 `17:00` 自动执行日线同步与完整性审计
- 对非豁免股票实现“发现缺口 -> 自动补偿 -> 复审”的闭环
- 对整日缺口和单股断档分别建模与修复
- 对长期多源失败股票采用“自动候选 + 人工确认”的混合豁免模式
- 明确区分可阻断错误、可重试错误、正式豁免对象
- 让后续筛选、回测、因子构建只消费“审计通过的交易日”

## 三、非目标

本次迭代不做以下事情：

- 不重构所有数据源 fetcher 的底层实现
- 不引入复杂的 Web 管理界面来维护豁免列表
- 不修改与 K 线完整性无关的策略逻辑
- 不在本轮把所有历史缓存/局部分析缓存彻底拆表，除非实现阶段发现这是必要前提

## 四、设计原则

### 1. 非豁免股票必须补齐

只要股票处于正常管理范围内，且未被正式确认为豁免对象，就必须纳入完整性要求。

“同步过一部分即可继续运行”不再等价于“数据健康”。

### 2. 临时失败不阻塞主任务，但不能静默丢失

网络超时、限流、单源异常、瞬时连接失败等场景，不应直接视为“该股票无数据”。

这类失败应当：

- 不阻塞当次主流程
- 进入补偿队列
- 在审计结果中记录为待修复项
- 后续重试成功后自动闭环

### 3. 长期无数据股票使用受控豁免

对长期、多源、反复失败的股票，不采用“永久硬编码白名单”，而采用混合模式：

- 系统自动将其标记为候选豁免
- 由脚本/数据库方式人工确认后，才能成为正式豁免
- 豁免不是永久不可变，后续如果成功拉到数据，应自动恢复为正常对象

### 4. 审计结果优先于局部同步结果

同步阶段只负责尽量拉到数据。

是否“已经完整”、某个交易日是否可被下游消费，最终由审计阶段判定，而不是由某一次同步调用的局部成功率判定。

## 五、数据分类、成功口径与状态机

### 1. 任务结果口径

为避免“主任务完成”和“数据已经健康”混为一谈，本次设计明确区分三种任务结果：

- `succeeded`
  - 本次目标交易日不存在未解决的非豁免缺口
  - 可以宣告当次治理任务闭环完成
- `degraded`
  - 主任务已完成，不阻塞下游主流程
  - 但仍存在待人工确认的 `candidate_skip` 或待后台重试的 `pending_retry`
  - 不能宣告数据健康，仅表示系统已进入受控降级态
- `failed`
  - 存在阻断型故障，或治理前置条件缺失，导致本次任务无法安全判断/执行
  - 不能将该次治理结果视为成功

### 2. 下游可消费口径

除 `run_result` 外，再单独引入 `pass_status`，作为下游唯一消费真相源。

- `passed`
  - 该 `trade_date` 在本次审计声明的 lookback 窗口内已通过完整性校验
  - 允许被 `FactorService`、筛选、回测和其它下游任务消费
- `not_passed`
  - 该 `trade_date` 仍存在未解决问题，或当前运行结果不足以下游安全消费

固定映射规则：

- `run_result = failed` -> `pass_status = not_passed`
- `run_result = degraded` -> `pass_status = not_passed`
- `run_result = succeeded` 且窗口覆盖满足要求 -> `pass_status = passed`
- `run_result = succeeded` 但窗口覆盖不满足下游任务要求 -> 对该下游任务仍视为 `not_passed`

任务结果与股票状态不是同一层概念：

- `candidate_skip` 可以让任务处于 `degraded`，但不能让任务被视为 `succeeded`
- 只有当未解决问题全部被修复，或被人工批准为 `approved_skip` 后，任务才能回到 `succeeded`
- `pending_retry` 在当次任务结束后统一归入 `degraded`，不会直接判成 `failed`
- 一旦任务结果为 `degraded`，该 `trade_date` 不得被下游当作“审计通过”

### 3. 状态主体

本次治理的主状态主体不再是“股票当前状态”，而是“缺口记录（gap）”。

原因：

- 豁免需要支持股票级和日期区间级作用域
- 同一只股票可能历史某段区间 `approved_skip`，但当前窗口已经健康
- `day_gap` 与 `symbol_gap` 本身也需要独立生命周期

因此建议采用：

- `gap 状态`
  - 作为真正的治理状态主体
- `股票摘要状态`
  - 作为基于当前审计窗口聚合出来的派生视图

### 4. gap 状态

- `healthy`
  - 当前 gap 已解决或不存在
- `pending_retry`
  - 当前 gap 判定为临时失败，需补偿重试
- `candidate_skip`
  - 当前 gap 连续多次、多源失败，系统自动标记为候选豁免
- `approved_skip`
  - 当前 gap 经人工确认后生效的正式豁免

`recovered` 不再作为长期驻留状态，而作为审计历史中的一次恢复事件保留。股票在恢复后应回到 `healthy`，同时记录：

- `last_recovered_at`
- `last_recovery_reason`

### 5. 股票摘要状态

股票摘要状态只服务于界面、日志和候选豁免清单，不作为主判定依据。

摘要规则建议为：

- 当前窗口内无未解决 gap -> `healthy`
- 存在 `pending_retry` -> `pending_retry`
- 不存在 `pending_retry`，但存在 `candidate_skip` -> `candidate_skip`
- 当前窗口内所有 gap 均为 `approved_skip` -> `approved_skip`

### 6. 状态转移条件

首版建议采用以下默认规则：

- `healthy -> pending_retry`
  - 单次治理任务中出现 `retryable` 失败
- `pending_retry -> healthy`
  - 后续补偿或下次治理任务中成功补齐当前审计窗口缺口
- `pending_retry -> candidate_skip`
  - 连续 `3` 次治理任务失败
  - 且至少有 `2` 个数据源尝试记录
  - 且最近 `3` 次中无成功获取记录
- `candidate_skip -> approved_skip`
  - 通过数据库/脚本人工确认
- `candidate_skip -> healthy`
  - 在人工确认前已成功补齐当前审计窗口缺口
- `approved_skip -> healthy`
  - 连续 `3` 次治理任务成功获取到有效数据
  - 且当前审计窗口中的相关缺口已补齐
  - 同时写入一条 `recovered` 事件记录

### 7. 失败原因分类

建议将失败原因明确分为三类：

- `blocking`
  - 系统性故障、数据库错误、关键依赖不可用
  - 应阻断任务或至少阻断“同步成功”结论
- `retryable`
  - 超时、连接失败、限流、单源异常
  - 不阻断主流程，但必须进入补偿队列
- `skip_eligible`
  - 多源多次验证后确认的长期无数据场景
  - 仅在人工确认后才从分母中排除

### 8. 豁免生效原则

豁免只有在 `approved_skip` 状态下才正式生效。

换言之：

- `candidate_skip` 仍然算“未闭环问题”，只能把任务降级为 `degraded`
- `approved_skip` 才能从完整率分母中扣除
- 恢复成功后应自动退出豁免统计并回到 `healthy`

## 六、核心流程设计

### 1. 每日 17:00 主任务

主任务统一设置为每个交易日 `17:00` 执行。

`17:00` 的语义定义为：

- 使用 `Asia/Shanghai` 时区
- 仅针对 A 股市场
- 目标 `trade_date` 为“当日已收盘的最新中国市场交易日”

目标日期解析优先级：

1. 显式传入的 `trade_date`
2. 官方交易日历中“今日是否为交易日且已过收盘”的判定结果
3. 如果交易日历不可用，则禁止自动推导新的 `trade_date`，任务直接进入 `failed`

交易日历不可用时，首版采用保守策略：

- 不自动发起“新增交易日”的治理
- 不自动补写新的 `trade_date`
- 仅允许显式传入 `trade_date` 的人工重跑
- 不允许自动生成新的 `approved_skip`

对于 17:00 后数据源晚到的情况：

- 17:00 任务负责启动治理闭环，而不是承诺 17:00 时刻立刻完整
- 允许在当次任务内部执行短周期补偿重试
- 若补偿窗口结束后仅剩 `pending_retry` 或 `candidate_skip`，则任务状态为 `degraded`
- 若无法安全确定目标 `trade_date`、无法访问关键存储、或规则前置条件缺失，则任务状态为 `failed`

推荐执行顺序：

1. 解析当日目标交易日
2. 运行增量同步
3. 运行完整性审计
4. 对缺口执行补偿
5. 补偿后立即复审
6. 输出审计报告与候选豁免清单

### 2. 同步阶段

同步阶段的职责是“尽量写入当天应有数据”，但不再承担“覆盖率够了就默认健康”的职责。

同步规则需要调整为：

- 不再用 `80%` 或类似覆盖率阈值直接放弃剩余缺口
- `fetch_failed` 不再直接视作普通可忽略失败
- 对于失败股票，至少要区分：
  - `retryable`：进入补偿队列
  - `candidate_skip`：进入候选豁免记录
  - `blocking`：记录为主任务失败或部分失败

### 3. 审计阶段

审计阶段负责判断“哪些数据应该存在但实际不存在”。

审计粒度必须覆盖两种情况：

- `day_gap`
  - 某个交易日大面积缺失
- `symbol_gap`
  - 某只股票在应有日期范围内存在中间断档

应有集合的定义原则：

- 股票范围来自 `instrument_master` 中正常管理的活跃股票
- 日期范围来自正式交易日历，不再从单一股票数据反推
- 每只股票的应有起始日期取：
  - `max(list_date, 审计窗口起点)`
- 下列对象应在进入差集计算前先从“应有集合”中排除：
  - 尚未上市股票
  - 已退市/终止上市股票
  - `listing_status != active` 的暂停上市对象
  - 已登记的 `approved_skip` 日期区间
  - 已登记的 `approved_skip` 股票级豁免
- 正常停牌不依赖 `listing_status` 推断，首版统一通过“停牌区间真相源”处理：
  - 优先使用显式登记的 `approved_skip(reason_type=suspended_range)`
  - 若后续实现阶段接入更可靠的停牌真相源，可再替换该入口
  - 已批准的按股票或按日期区间豁免记录
- 正式豁免股票不纳入分母

为支持“下游只消费审计通过交易日”，审计阶段需要持久化完整的审计真相源：

- `kline_audit_runs`
  - 粒度：单次治理任务
  - 记录运行时间、目标 `trade_date`、窗口范围、规则版本、配置快照、最终结果
- `kline_audit_trade_dates`
  - 粒度：`market + trade_date`
  - 记录该交易日是否已通过审计、未解决缺口数、`run_result`、`pass_status`、最后审计时间
- `kline_audit_gaps`
  - 粒度：稳定 `gap_key`
  - 记录真正的最小治理对象，而不是一次性快照
  - 首版明确支持两类 gap：
    - `market_day_gap`
      - 表示某个 `trade_date` 的市场级整日缺口
      - `code` 允许为空
      - `missing_date_from = missing_date_to = trade_date`
    - `symbol_range_gap`
      - 表示某只股票在一段连续日期区间内的缺失
      - `code` 必填
      - `missing_date_from <= missing_date_to`
  - 建议至少包含以下字段：
    - `gap_key`
    - `gap_scope`
    - `market`
    - `trade_date`
    - `code`
    - `gap_type`
    - `missing_date_from`
    - `missing_date_to`
    - `status`
    - `retry_count`
    - `failure_count`
    - `last_error`
    - `related_skip_registry_id`
    - `created_at`
    - `updated_at`
  - 若同一股票在同一审计窗口中存在多个不连续断档，必须拆成多个独立 `symbol_range_gap`
- `kline_audit_events`
  - 粒度：状态迁移事件
  - 记录 `gap_key` 如何从 `pending_retry` 进入 `candidate_skip`、何时被批准、何时恢复

下游消费契约：

- `FactorService.get_latest_trade_date()` 不再直接按 `stock_daily` 覆盖率猜测最新交易日
- 改为查询 `kline_audit_trade_dates` 中最近一个 `pass_status='passed'` 的 `trade_date`
- 若该表无可用结果，则返回空并显式提示“最新交易日尚未通过 K 线审计”
- 任何显式传入 `trade_date` 的筛选、回测或脚本任务，在读取该日数据前都必须先校验：
  - 对应 `trade_date` 是否存在通过记录
  - 对应通过记录的窗口范围是否覆盖本任务所需 lookback
  - 对应规则版本是否与当前任务允许的版本兼容

### 4. 补偿阶段

补偿按缺口类型分别处理：

- 对 `day_gap`
  - 优先按交易日进行整日批量补数
- 对 `symbol_gap`
  - 按股票代码与缺失日期区间精确补数
- 对 `pending_retry`
  - 限次重试，多源 fallback
- 对 `candidate_skip`
  - 只继续记录失败与尝试来源，不阻塞主流程，但当次治理结果最多只能为 `degraded`

补偿完成后，必须立刻复审，而不是等到下一个调度周期才知道有没有补齐。

## 七、豁免机制设计

### 1. 采用混合模式

本次明确采用“自动标记候选 + 人工确认生效”的混合模式。

这意味着：

- 系统自动发现反复失败股票
- 系统不会自动把它们直接从完整率分母中排除
- 仍需要通过数据库/脚本确认后，才变成正式豁免

### 2. 首版审批入口

首版使用“数据库/脚本方式”作为人工确认入口，优先保证稳定可用。

不在本轮要求新增 API/UI 管理面板。

### 3. 豁免登记表建议

建议新增一张登记表，例如 `kline_skip_registry`，字段至少包括：

- `code`
- `date_from`
- `date_to`
- `status`
- `reason_type`
- `reason_detail`
- `failure_count`
- `sources_tried`
- `first_seen_at`
- `last_checked_at`
- `approved_by`
- `approved_at`
- `expires_at`
- `notes`

豁免作用域要求支持：

- 全股票范围豁免
- 指定日期区间豁免

首版默认以“日期区间可选、股票级可退化”为设计，不把所有豁免都强制建模成整只股票全历史永久豁免。

### 4. 初始候选样本

可以将以下股票作为首批候选样本导入登记表：

- `000552`
- `300067`
- `301022`
- `603056`

但它们首版应只进入候选或待确认状态，而不是直接作为永久白名单写死在代码里。

### 5. 自动恢复

如果某只已进入 `candidate_skip` 或 `approved_skip` 的股票，后续补偿任务成功拉到了有效数据，且当前审计窗口的相关缺口已补齐，应：

- 写入一条 `recovered` 审计事件
- 将股票状态恢复为 `healthy`
- 重新纳入完整性审计分母

## 八、调度与执行策略

### 1. 每日任务

建议新增一条独立的 `KlineGovernanceScheduleService`，沿用仓库已有 schedule service 风格，而不是把治理逻辑直接堆进 `main.py`。

新增或改造一条 K 线治理任务，在每个交易日 `17:00` 执行。

建议任务职责覆盖：

- 当日增量同步
- 近端审计
- 近端窗口默认不小于“当前下游最大 lookback 需求”
- 近端补偿
- 复审与告警输出

为避免下游因子计算读取到历史断档，首版近端审计窗口应至少覆盖：

- 最新交易日
- 以及下游因子/策略所需的最近回看窗口

具体窗口大小可在实施计划中绑定为配置项，但不能低于当前下游最大 lookback 需求。

`passed` 的定义必须绑定窗口范围：

- `trade_date` 通过，不等于“全历史无缺口”
- 它只表示：在该次 `kline_audit_runs.window_start ~ window_end` 范围内，目标 `trade_date` 的所需 lookback 已通过审计
- 因此 `kline_audit_trade_dates` 需要保存最近一次通过所对应的窗口范围和规则版本

### 2. 周期性深度审计

除每日任务外，建议保留一条低频深度审计任务，例如每周一次，用于扫描更长窗口内的历史断档。

职责包括：

- 检查最近 `250-400` 个交易日
- 识别历史中间断档
- 修复存量坏数据
- 重新评估候选豁免对象

## 十、测试关注点

### 1. 缺口识别正确性

必须覆盖：

- 某个交易日全市场大面积缺失能被识别为 `day_gap`
- 单只股票中间缺日能被识别为 `symbol_gap`
- 已上市前日期不会被误判为缺口
- 正式豁免股票不会继续计入完整率分母

### 2. 状态机正确性

必须覆盖：

- 单次失败进入 `pending_retry`
- 连续 `3` 次、多源失败进入 `candidate_skip`
- 经脚本确认后进入 `approved_skip`
- 后续连续成功并补齐缺口后回到 `healthy`
- 恢复过程会写入 `recovered` 事件

### 3. 主流程不阻塞

必须覆盖：

- 非阻断失败不会让整个分析任务卡住
- 正式豁免股票不会导致主流程失败
- 非豁免股票缺口仍会进入补偿闭环
- `degraded` 的交易日不会被下游误当成通过

### 4. 完整率约束

必须覆盖：

- 非豁免股票完整率必须达到 `100%`
- 候选豁免股票在未批准前，仍然不能从分母中排除
- `fetch_failed` 不能再被直接当成“同步成功”

### 5. 定时任务行为

必须覆盖：

- `17:00` 任务注册正确
- 目标 `trade_date` 解析正确
- 非交易日不会误执行同步逻辑
- 交易日历不可用时任务进入 `failed` 且禁止自动推导新日期
- 每日任务与深度审计任务可以独立运行

## 十一、存量数据治理策略

除新增闭环外，还需要处理当前数据库中的存量坏数据。

建议分两步：

1. 先运行独立审计脚本，导出所有 `day_gap` 与 `symbol_gap`
2. 再按缺口类型执行一次性修复

优先修复对象：

- 近端交易日的整日缺口
- 影响当前筛选/因子计算的中间断档
- 总行数异常低但应处于正常管理范围内的股票

## 十二、主要风险

### 风险 1：豁免条件过松

如果候选豁免很容易自动晋升为正式豁免，可能会把本应补齐的股票错误排除。

缓解建议：

- 自动只到 `candidate_skip`
- 正式豁免必须人工确认
- 豁免记录保留过期时间和复核时间

### 风险 2：主任务时长过长

同步、审计、补偿、复审串行执行，可能导致 `17:00` 任务耗时偏长。

缓解建议：

- 每日任务优先覆盖近端窗口
- 深度历史审计放到低频任务
- 区分“主任务完成”与“后台补偿完成”

### 风险 3：当前数据模型职责混杂

如果 `stock_daily` 同时承载全市场权威库和局部分析缓存，可能持续制造“看起来像缺口”的噪音。

缓解建议：

- 实现阶段先通过审计口径和状态标记规避误判
- 如问题仍无法消除，再考虑拆分权威库与临时缓存职责

## 十三、验收标准

当满足以下条件时，可认为本次工作完成：

- 每个交易日 `17:00` 自动执行 K 线同步与审计任务
- 非豁免股票在审计窗口内的 K 线完整率达到 `100%`
- 临时失败不阻塞主流程，但能进入补偿闭环
- 长期无数据股票通过“候选 -> 人工确认 -> 正式豁免”管理
- 已豁免股票后续恢复后能自动退出豁免
- 下游只基于审计通过的交易日构建因子与筛选结果

## 十四、实施建议

建议按以下顺序推进：

1. 新增豁免登记表与数据库读写接口
2. 编写候选豁免确认脚本
3. 实现独立完整性审计服务
4. 实现补偿服务与复审逻辑
5. 改造增量同步链路，去掉“缺口可放过”逻辑
6. 改造主流程与调度，接入每日 `17:00` 任务
7. 清理当前数据库中的存量坏数据

这样可以先建立审计真相源，再逐步替换当前容易放过缺口的链路逻辑，降低回归风险。
